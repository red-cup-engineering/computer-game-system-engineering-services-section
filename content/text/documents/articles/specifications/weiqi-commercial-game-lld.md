# Complete game-session and customer-economy detailed design

**Stage boundary:** This is an LLD candidate derived from the existing [SRS](weiqi-commercial-game-srs.md) and [HLD](weiqi-commercial-game-hld.md), both still awaiting independent owner/receiver admission. It neither authorizes fabrication nor claims to be a test, deployment, accepted money flow or player result. The native Data/Code specification admission and its producer/consumer closure must precede construction. An existing supplier's current export is evidence of available code, NOT evidence of a running composite.

**Customer:** Causeway Public Games and an actual player who can start a real fight, face a credible recurring rival, hear and see the real position, finish, replay, and optionally buy a source-specific, genuinely delivered analysis. Preserve the user-visible free legal game. The commercial objective is positive realized net contribution and meaningful repeat play, never merely checked compliance or new interfaces.

## II. Exact match and event data contracts

### A. Match authority (game rules distinct from accept-log clock)

Current source shape: createWeiqiMatch(config, {black,white}) creates a principal-attributed session, accepted log and stateHash. admitWeiqiMatchCommand(match, {principal,idempotencyKey,expectedVersion,command}, receivedAt) validates and appends a command. The accepted log entry is an ordered Cartridge move with its principal, idempotency key, expected session version, config ID, frozen Go command and received timestamp.

**Critical witnessed counterexample:** When the first player proposes a dead-stone set, the match log and pendingSettlement change, but the game session.version need not change. Therefore session.version is NOT the revision of all accepted match operations, and using it alone allows a second concurrent proposal based on stale accepted history. Preserve legitimate opposing counterproposal and mutual agreement, but distinguish concurrency freshness.

**Proposed native replacement contract, owned by the same match source, not an app-side patch:**

- MatchAuthorityV3 contains immutable config/ruleset, distinct authenticated players, Cartridge log, derived session and stateHash, pendingSettlement, and **matchRevision**: exact nonnegative integer equal to log.length. **gameVersion** is the engine's existing session.version. These two counters have different meanings and must never be aliased.
- AdmitMatchRequestV3 carries matchId, principal, idempotencyKey, expectedMatchRevision, expectedGameVersion, and one valid Go command. Timestamp comes from the authoritative host, not the browser. All fields are versioned, validated and typed by the owning Data/Code admission.
- Identical replay of one previously accepted idempotencyKey with identical principal, game/match preconditions and command returns that original accepted operation identity and derived result without appending. Same key with changed principal/body/precondition **refuses idempotency-conflict before any state change**, even if the game has since advanced.
- A new command is permitted only if expectedMatchRevision equals current log.length **and** expectedGameVersion matches the source-derived engine version. Version disagreement refuses stale-match or stale-game respectively with a current authorized view. Each admitted command, **including a pending settlement proposal**, appends exactly once and advances matchRevision once. Go session.version advances only when the engine's actual game transition does.
- A proposal cannot be silently overwritten by a stale participant. The now-informed opponent can confirm the exact same normalized dead group set or issue a legitimate different counterproposal at the fresh log revision. Exact confirmation invokes the existing engine settlement command and terminates the match when permitted by its rules. A changed proposal after both players have agreed cannot change a final result.
- Authoritative persistence is one atomic state replacement on the Durable Object after engine admission. A write is not acknowledged to the browser, other players, Qwzspace or Footing until durable commit succeeds. If the host crashes before acknowledgment and the same key is retried, recover the already-committed record; after a write refusal the prior log remains unchanged. This state machine must have a captured-in-source migration and full replay proof before enabling a new Worker.
- verifyWeiqiMatchV3 replays every accepted entry to reconstruct **both** counters, authenticated participant, session checkpoint, the pending settlement and state hash; a mismatched carried checkpoint or missing/duplicated sequence number refuses. No shared helper may create an alternative Go adjudicator.
- Historical v2 records require a source-owned replay migration that reconstructs matchRevision from each accepted log and preserves gameVersion, principals and actual pending agreements. Mixed old/new clients are refused with a recoverable explicit version response rather than a permanent compatibility shim. V3 service must not assume a first dead-stone proposal consumed a Go move.

**Two-positive/three-negative design assay:** (1) Black and White play legal 9×9 moves; counters advance together; reload yields identical log/hash; (2) first player proposes dead mask after two passes, matchRevision advances while gameVersion stays put, informed opponent agrees or counterproposes; (3) two parties simultaneously submit proposals using the same old revision—one wins; the stale one refuses, no overwritten pending state; (4) same idempotencyKey with a different mask or beneficiary refuses; (5) a serialized checkpoint with altered log, principal or stateHash refuses replay. Exercise under both area and territory scoring and the documented ruleset version.

### B. Match transport and authorized observation

Keep the existing one-match Durable Object as the single writer, but qualify it via the *existing* shared identity/session provider. An online player is a durable permitted actor, not simply a copied URL secret. A spectator gets explicitly admitted read-only board projection; no private correspondence, checkout, provider keys or opponent session credentials. No actor can use a room connection, Cast persona object or a client-supplied role as authorization to mutate another player's match.

The match response is an immutable MatchProjectionV3: {matchId, matchRevision, gameVersion, stateHash, toMove, boardProjection, result, acceptedEvents, lastMoveIdentity}. AcceptedEvents identify the exact admitted source revision and engine semantic-event type; they contain no raw secrets. Resume asks for matchRevision, receives a verified checkpoint and consecutive events, or a bounded full snapshot if deltas aged out. A rendering failure or dropped broadcast may repeat a revision, but an observer ignores already-consumed event identities and **never** posts duplicate Go commands. An offline guest match can continue on the current local kernel with an explicit unranked/unpaid indicator; it cannot forge an online match on reconnection.

### C. Cloudflare Durable Object concurrency and publication

Cloudflare's [current single-thread/input-output-gate and storage-transaction rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) are a concrete design constraint, **not** evidence of this app's runtime health. Awaiting a non-storage network I/O may interleave requests even inside one Durable Object; serial instance identity alone is not a transaction. Admit/read the authoritative match and append one new Cartridge entry under the same **storage transaction or source-proven equivalent**; compare expectedMatchRevision and idempotency key *inside* that atomic boundary rather than only in a preceding browser or in-memory check. Never await external Cast/KataGo/Qwzspace/Stripe calls while holding a match-storage lock or blockConcurrencyWhile. Commit the new matchRevision/log/checkpoint together; publish observer frames only after durable receipt, with monotonically increasing source revision and deduplicable event identity. For stale contenders, return the latest permitted source projection without writing. Replay on cold start and independent event-gate observation must establish that an interrupted write is either wholly present and idempotently readable or wholly absent.

Cloudflare's [current object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/) also permits eviction, hibernation and reinitialization; no accepted game outcome may depend on a JS instance surviving. Existing match-worker.mjs uses Durable Object fetch routing; newer Cloudflare guidance favors RPC method interfaces on supported compatibility dates, but this is an **architectural migration choice for detailed design**—do not build a parallel fetch and RPC authoritative log. Choose one native transport entrance after examining actual other Qwzspace and Worker consumers, and independently test old-session refusal/recovery at the public hostname. The existing static Worker configuration remains untouched until the composed installation is admitted.

## III. Modern opponent, gameplay and presentation details

### A. Rival implementation and performance

Use Cast createRunner({persona,policy,transport,seed,maxSteps}) with the source-owned adapter interface connect/observe/sendIntent/disconnect. The observer returns only a verified MatchProjection plus permitted Go state. The chooser may use the existing weiqi-engine legal moves and its *current* Pondering Monte Carlo tier for offline play. For a stronger declared rival, the existing Go process provider supplies GTP/KataGo requests; the process-capable host resolves model, engine version, search visits, observed latency and cost **before** the encounter is offered. A policy never fabricates an external engine's ability from a Cast dialogue label.

One bot command passes through the same AdmitMatchRequestV3 as a human, with independent actor identity, match revision and idempotency. A bot cannot act twice on one turn, skip an authentic opponent, declare the game outcome, or mutate a past record. A timeout returns a visible pending/rival-unavailable state with the **same** match still recoverable. Opponent strength is qualified from actual head-to-head results across seeds, ranks/rulesets and held-out moves; no unmeasured kyu or professional skill claim. Rematch reuses the rival character but creates a separate match identity.

### B. Game-feel presentation contract

The game board remains a specialized accessible Go board, using the existing correct point hit testing/touch magnifier and generated kernel; do NOT replace it with an unrelated 3D world or copy a new renderer merely because Qwzspace exports one. Qwzspace is hired for scene frames, time-based tweens, seeded particles, result celebration and optional room/presence. Resonator is hired for one genuinely mixed WebAudio cue stream with volume persistence, muted and reduced-motion variants. Define one versioned, pure GameMoment projection from accepted engine events to visual/audio decisions, not an isolated handler per button.

The accepted-moment priority is: game settlement/victory, captures, threatened/escaped atari, connection/eye, ordinary legal placement/pass. A single move may produce multiple **true** events; the projection plays the primary accent and supplementary restrained cues without repeating the move or visually hiding the new stones. Anticipation under pointer/touch is an explicitly provisional and cancelable preview; placement impact occurs only upon match acceptance. Replay derives the same order and seeded effect family from immutable matchRevision/move identity; no cash or rating is triggered by a replayed animation.

Minimum complete interaction: first playable board in at most two user actions from the storefront, immediate pointer/touch acknowledgment, readable ownership and turn, meaningful accepted move impact, a strong/opponent-state response, legible capture, coherent resolution, and one-click rematch/replay. Interface hierarchy must privilege the game canvas/board and action controls over glossary/notes, not require the learner to enter a lesson. Audio failure, low graphics capacity or reduced motion keeps correct move acknowledgment, visible outcome and keyboard/screen-reader affordances. Existing static local game remains operable without the online host.

**No source code in this LLD:** the source-aware native fabricator must derive the actual event-algebra types, semantic projection and consumer modules after SRS/HLD/LLD admission. Qwzspace and Resonator source signatures above are incumbent API evidence, not an assertion that their existing bundled resources already satisfy the new projection contract.

### C. WXWQ tactic/strategy, sect-visitor and instruction port

One actual play recording is projected through weiqi-engine and the existing immutable Study frames. The implemented **planTacticalTryouts(frames,{color,limit})** is a pure engine-side projection; results carry observed side, source move, source version, prior branching version, semantic tactic and science term address. Capture/ko/atari/connection/eye observations from the original rules engine qualify as **tactical events only**, not a complete strategy score, a nation-specific style, an actor identity or a monetary right. Its checked-in generated browser module must equal the native builder's output. The existing Weiqi Study page receives the full original history and creates an alternative prefix through studyBranchAt; trying a move calls the original admitWeiqiGameCommand and passes a visitor's one-move test only if the actual admitted events include the named target. Imports replace the original recording and cannot inherit another game's challenge address. Black/White event filters cannot silently become authenticated human principals. The original match continues to exist unchanged.

The authored [Opponent Cast](https://github.com/red-cup-engineering/computer-engineering-services-section/blob/main/services/computer-systems-engineering-services-section/services/computer-game-system-services-section/services/go-engine-services-section/apps/weiqi-platform/content/text/documents/articles/design/opponent-cast.md) is the retained fictional character input; actual agent-persona persistence, scheduled sect encounters, room dialogue and distinct policies require the shared Cast runner, stable actor identity and Qwzspace. ## IV. Competition and retained game identity

Footing submitDailyRun consumes {store,today,body,dailySeed,replayFn,requireEntrantKind} and replays the actual submitted sequence to determine the score. For a ranked Weiqi challenge, the host must own the start/end/deadline, contest seed, actor, unique claim/attempt ID, score rule and replay source. Today's client-local Puzzle Rush timer and localStorage record do **not** meet that authority. The server recomputes the score from one exact puzzle/rules corpus revision, accepted attempts and trusted timing. Repeat same attempt returns the prior outcome; a second scored attempt for the same day/actor is refused under Footing's lock. A practicing person may continue using the local challenge without an authoritative leaderboard. A sibling existing arcade game remains the second real consumer of the shared competition provider, not a generated test harness in place of a product.

## V. Paid personalized analysis lifecycle

The existing fixed Digital Goods offering/pointer remains true but **cannot** be used to misrepresent a personalized review. Web Commerce must qualify a game-neutral **CommissionedWorkFulfillment** capability over its current fixed-offer Stripe service and durable entitlements; the first two real product consumers must justify its shared contracts. Proposed product-specific immutable WorkReview intent includes {workId, merchant, buyerActor, matchIdentity, matchStateHash, SGF/sourceDigest, ruleset, quoteRevision, chargedAmount/currency, analysisModelVersion, analysisBudget, eligibility/rights, expiry}. The customer must authorize price and terms; the trusted provider binds the quote rather than accepting browser amounts.

The permitted state machine is PREPARED → CAPACITY_RESERVED → CHECKOUT_PENDING → PAID → QUEUED → RUNNING → FULFILLED; payment/capacity errors instead yield EXPIRED, COMPENSATING, REFUNDED or unequivocally FAILED with a separately reconciled obligation. A status may never skip verified payment into entitlement, or mark report delivered from an unconfirmed worker response. Source game and paid work have **different identities**; the paid work references one immutable admitted game, and the actual Stripe merchant/customer identity is authoritative for money.

Capacity is checked before enabling purchase: process-capable host, licensed actual KataGo/GNU Go model, max visits, protected report storage, result bytes and time/cost bound. When the charge is provider-confirmed, create the bounded analysis lot exactly once and store its durable current state. Provider request/reply and retry must preserve one work ID; a network timeout is unresolved until original provider transaction and work custody are reread. A canceled, revoked or refunded work cannot be used as a second authenticated download. Authenticated account retrieval checks the same principal and matching entitlement. The report includes source match ID/digest, board move variations validated through weiqi-engine, independent Go engine/model version, compute budget, glossary-linked plain explanations, analysis uncertainty, export and a rematch route; each report's delivered bytes and content identity are immutable.

**Analysis-offer economic acceptance:** Merchant shows actual settled gross amount minus processing fee/refund, compute and network, rights, operating acquisition and support cost; buyer can reopen the exact completed report on another authorized device. The optional $2.99 analysis hypothesis is unapproved and may be rejected if the qualified unit cost cannot yield positive net contribution. A returning user who declines payment must still enjoy a legitimate free match. This completes **one optional SKU's** receiving, not the flagship game's commerce or its wider education and entertainment economy.

## VI. Optional financial participation and separate IdleGame

The current Energy Bank zbdBackend remains a no-network stub and its resolveBackend may fall back to mock. **It is not selected for any monetary effect.** Game-achievement validity, external person/beneficiary eligibility, reserve/treasury liability, external payment authorization, provider acceptance, final Lightning settlement and player receipt are distinct. Design the generic merchant financial contract before choosing the provider: {awardIdentity, originGame/acceptedResult, liableMerchant, playerActor/recipient, asset, exact integer units, amount, reserveReference, permittedJurisdiction, providerAgreement, externalTransferReference, finalityEvidence}. A repeated award with any changed amount, direction, beneficiary or principal must refuse even when the ledger reference exists. Never return CLEARED for a mere existing ID, mock payment or ZBD API key string; no automatic different-provider substitution. The external provider's *actual current endpoint* chooses whether the monetary unit is sats or msats; do not hard-code a conversion into a different product. The first award requires lawful documented provider participation and an independent merchant/recipient cash receipt.

IdleGames remain a separate public product and actual paying-user research question. Their simulator must calculate deterministic bounded resource transitions and explicitly supported pause/catch-up, with user choices and true incremental value; it may reuse the shared presentation, Footing and real treasury provider but cannot turn background time or Go-game losses into fictional bitcoin. The separate existing FALL idle-game concept is a design input, not evidence of an installed game or accepted cash earning. Both market lines need measurable cohorts, out-of-time demand forecasts and their own net unit contribution. No arbitrary in-game ENERGY exchange rate establishes real money value.
