# Themeable game engines, and the cross-game unlock

Founder idea, three layers, each deeper and more valuable than the last.

## 1. A slot engine where a theme IS a ruleset

The genre trope stated plainly: a slot machine is an engine, and each
theme is a different reel/payline/feature ruleset over it. Build the slot
engine once; a tarot theme, a Tideline theme, a heyoka theme are each JSON
rulesets (reel strips, paylines, feature triggers, RTP target) over the
same engine. This is not new work from zero — the house already extracted
`@red-cup-engineering/parlor-kernel`'s `paylines.mjs` as the shared slot
math upstream of both parlor and the casino's "Tideline Treasures" slot.
The slot engine is the natural next parlor-kernel lift; a tarot theme is
its first showcase ruleset.

## 2. Generalized game-asset + theming, seated in engineering

The real idea underneath: a **theming primitive** — game assets and
rulesets as DATA over shared engines — seated in engineering, consumed by
every game. This is the house's own products-as-data / parameterization
law (play.561.group and mud.561.group already run one
`games-catalog-storefront` engine over different JSON) applied to game
CONTENT, not just catalogs. onestone (tiling-agnostic already:
square→hex→rhombille) becomes themeable; the casino slot becomes one
theme instance; new games are new rulesets over engines that already
exist. It threads five-custody: science (the game/agency theory), the
theming primitive in engineering, operations for how themes ship,
561-group as owner, public as the games fleet.

## 3. The cross-game unlock — the differentiator (a mini-game empire)

The monetization the trope invites — "pay to unlock a new slot theme,
theme your match-3" — but with the twist no incumbent offers: **the unlock
carries ACROSS games.** Buy the tarot theme once; it themes the slot, the
match-3, the tiles, wherever it applies. That is a cross-title entitlement,
not a per-game microtransaction — the buyer accrues a portable cosmetic/
content library across a whole fleet, so every new game launches with an
install base that already owns things for it. This is where the house
receipts-native identity becomes a product feature, not plumbing: the
entitlement is a witnessed, portable receipt the player owns, honored by
any house game — meet-then-beat the per-game-walled-garden model of every
match-3 and social-slot on the app stores.

Fences, per house law: the casino carries the only owner-ruled real-money
framing (tickets-for-play, 2026-08-29 direction) and stays paper/tickets,
never real-money wagering; the other games stay earn-only. A paid THEME
UNLOCK (cosmetic/content, not a wager) is a different thing from a
wager and is the sellable surface here — through the house storefront,
priced when the content isn't thin. Digital-first, and a strong theme
(the tarot set) is also the bridge to the physical tarot-mahjong /
crowdfund-to-fab idea (see the enterprise speculation note, same date):
the same generated art funds twice.

## Standing frame

Validate demand before seating (foundry law); build the theming primitive
in engineering ONCE and let games consume it (never per-game theme code —
that is the disease this note exists to prevent); nothing thin sold; the
cross-game entitlement rides the house's own receipt rail.
